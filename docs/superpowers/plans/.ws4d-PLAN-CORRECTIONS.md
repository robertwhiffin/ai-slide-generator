## 2. BLOCKING — the async engine-mode path runs through the JOB QUEUE, which the plan never mentions. And the payload key `mode` is already taken.

D0 states the placement rule as one sentence: *"Mode resolution must happen in the **chat route
handlers** at the top of the streaming path, with mode passed as a parameter to
`send_message_streaming` **defaulting to monolith**. MCP never calls those routes, so it is excluded
by its traffic path."* **The rule is right and the plan's picture of the path is wrong.** Measured:

`send_message_streaming` has exactly **two** backend call sites, and only one of them is a route:

| Call site | Reached from |
|---|---|
| `src/api/routes/chat.py:480` | the streaming route `POST /chat/stream` (handler def `chat.py:397`) |
| `src/api/services/job_queue.py:202` | `_run_streaming_generator` (def `job_queue.py:176`), reached from `process_chat_request` (`job_queue.py:71`), reached from `worker()` (`:214`), fed by `enqueue_job` (`:36`) |

**`POST /chat/async` (`submit_chat_async`, `chat.py:560`) never calls `send_message_streaming`
itself** — it enqueues a job. So does MCP: `src/api/mcp_server.py:242` calls the **same**
`enqueue_job`, onto the **same** queue, drained by the **same** `worker()`, into the **same**
`process_chat_request`. The async browser path and the MCP path are the same code from
`enqueue_job` onward.

**Consequence, and it is the r1 finding 1 defect reintroduced by the plan's own vagueness:** an
implementer who reads "the chat route handlers" and resolves mode inside `process_chat_request` or
`_run_streaming_generator` — the two places that actually sit "at the top of the streaming path"
for production traffic — **puts MCP on the graph.** An implementer who instead resolves it only in
the streaming route leaves the async route, which is the production path, permanently on the
monolith, and the DoD's "mode is sticky on the two entry points in scope" fails.

**The correct wiring is SIX edit points across TWO files, one of which the plan never names:**

| # | File:line | Change |
|---|---|---|
| 1 | `src/api/routes/chat.py:397` (streaming route body, before `:480`) | resolve mode, pass it to `send_message_streaming` |
| 2 | `src/api/routes/chat.py:560` (`submit_chat_async`) | resolve mode, put it in the job payload |
| 3 | `src/api/services/job_queue.py:71` (`process_chat_request`) | read it out of the payload with a monolith default |
| 4 | `src/api/services/job_queue.py:115-123` and `:137-144` | pass it at **both** `_run_streaming_generator` call sites — they are positional, and there are two (the `if ctx:` branch and the no-context recovery fallback) |
| 5 | `src/api/services/job_queue.py:176` | add the parameter to `_run_streaming_generator`, defaulting to monolith |
| 6 | `src/api/services/chat_service.py:825` | add the parameter to `send_message_streaming`, defaulting to monolith |

MCP is then excluded **structurally**, exactly as D0 wants, because `mcp_server.py:242` builds its
payload without the key and step 3's default is monolith. The recovery fallback at `:135` (jobs
replayed with no captured context) also defaults to monolith, which is the right direction to fail.

### The payload key must be `engine_mode`. It must NOT be `mode`.

**`mode` is already a key in that payload.** `src/api/mcp_server.py:253`:

    "mode": mode,
    "correlation_id": correlation_id,

with the comment *"Forward-looking: mode and correlation_id flow into the payload so the worker (and
logs) can see them even though v1 only executes generate-mode jobs."* That is MCP's
generate-vs-edit mode, an unrelated concept whose values are neither `"graph"` nor `"monolith"`.

A `payload.get("mode", "monolith")` read therefore returns MCP's `"generate"` on every MCP job. It
would *happen* to compare unequal to `"graph"` and fall through to the monolith, so the collision is
**safe by accident and not by design** — and the accident inverts the moment anyone compares against
`"monolith"` instead of `"graph"`, or logs the value, or adds a third engine. **Name the key
`engine_mode` everywhere: payload key, parameter name, and any test fixture.**

## 4. BLOCKING — `emit_slide_ready` belongs in ws4c's `event_emitter.py`, and it takes NO queue

Measured, ws4c ships `src/services/graph/event_emitter.py`:

`invoke_graph` (`src/services/graph/builder.py:184`) owns the ContextVar's lifecycle — it calls

## 5. BLOCKING — `slides_since_cursor` cannot reuse `releasable_positions`; that function reads GRAPH STATE, not rows

D3 says `slides_since_cursor(session_id, cursor)` is *"the release query over rows, reusing
`releasable_positions`' prefix rule"*. Measured, `releasable_positions`
(`src/services/foreman_service.py:209`) is a **module-level function taking `state: dict`** and its
body reads graph state through `scoped_vals`:

    covered   = _covered_positions(state)
    landed    = scoped_vals(state, "landed_positions")
    placeheld = scoped_vals(state, "placeheld_positions")
    committed = landed | placeheld
    for p in covered:
        if p in committed: result.append(p)
        else:              break        # gap: nothing past this point is releasable

**The polling path has no graph state.** `poll_chat` serves a request that may be handled by a
different uvicorn worker from the one running the graph, which is the whole reason D3 makes the
reorder buffer a query over committed rows. So:

- **`slides_since_cursor` re-implements the prefix rule over `session_slides` rows.** It does not
  import `releasable_positions` and cannot be handed a `state` dict it has no way to build. "Reusing
  the prefix rule" means reusing the **rule**: ascending scan, stop at the first gap, return the
  contiguous committed prefix above the cursor.
- **`releasable_positions` is not a `SessionManager` method.** `session_manager.releasable_positions(...)`
  raises `AttributeError`.
- Keep the two implementations' agreement pinned by a test that drives the same position set through
  both and asserts identical output — the divergence is otherwise invisible, and a placeholder row
  must release like any other position on both.

## 10. `_upsert_slide_row`: D2's conclusion is right, its location and its mechanism are both wrong

D2's central identity argument: *"`contextvars` do not cross a bare `threading.Thread`, so
`get_current_user()` inside `invoke_graph` returns `None` (`user_context.py:11`), `modified_by` is
`None`, and `_upsert_slide_row` inserts a NULL author (`slide_repository.py:104-107`) — no exception,
no failing test unless one asserts the author."*

**The conclusion holds. Three of its supporting facts do not.**

1. **`_upsert_slide_row` is defined in `src/api/services/session_manager.py:409`**, not in
   `slide_repository.py`. `slide_repository.py` imports and calls it at `:133`. A test that patches
   `slide_repository._upsert_slide_row` patches a name that does not exist in that module.
2. **`slide_repository.py:104-107` says the OPPOSITE of what the plan quotes it for.** Those exact
   lines are docstring text for the partial-mode UPDATE path:

       - If verification_record is None, the existing value is PRESERVED.
       - If deck_spec_slide is None, the existing value is PRESERVED.
       - If modified_by is None, the existing author is PRESERVED (final review
         F8: this used to null it unconditionally, so a reviewer rewriting HTML

   `modified_by=None` **preserves** the existing author on UPDATE. It was changed to do so
   deliberately, by a prior final review.
3. **The NULL author happens on INSERT, not UPDATE.** The INSERT path (`session_manager.py`, around
   `:519`) passes `modified_by=modified_by` straight into the `SessionSlide(...)` constructor, so a
   **new** row written with `modified_by=None` does store NULL.

**Why this matters for the test, not just for the prose.** A guard that writes a graph slide over an
**existing** row and asserts the author is not NULL **passes with the context copy removed**, because

## 18. STANDING INSTRUCTION added during the build — the absence-assertion trap

**Three tests on Task 2 alone had this identical shape, and all three survived the sabotage that should
have killed them.** None was visible by reading the test.

An assertion that a thing did **not** happen is usually also true when the code **never ran at all**:

| The test asserted | It is equally true when |
|---|---|
| `versions() == []` after a failing save point | the save-point call was never made |
| the slide row's author is unchanged | the write took the UPDATE path, which preserves the author regardless |
| "an `ASSISTANT` event arrived" as a proxy for incrementality | the whole turn completed before anything was read from the queue |

**So: assert the path was ENTERED, not that a table is empty.** Record the attempts (a spy, a counter,
a captured call list) and assert the entry count, then assert the outcome. A test whose only assertion
is an absence cannot distinguish "the guarded thing was handled correctly" from "the guarded thing never
executed", and it is the single member of its class that will survive you deleting the production call.

**Every task from 3 onward: for each test you write, ask whether deleting the production call it guards
would leave it green.** If yes, the test is measuring absence and needs an entry assertion.

## 21. Two prefix implementations are CORRECT, and §5/W-12 under-specified why

§5 (Ruling W-12) said `slides_since_cursor` must re-implement the prefix rule over rows because the
polling path has no graph state. That is right, and it left the SSE path's source unexamined while the
plan's single-query framing implied rows there too. **Measured by Task 3, and confirmed: the two
transports must read DIFFERENT sources.**

- **SSE** filters `releasable_positions(state)` by a turn-scoped cursor (`src/services/graph/nodes.py:185`).
- **Polling** scans `session_slides` rows (`src/api/services/session_manager.py:2031`).

**Why the SSE path cannot use rows:** on an **edit** turn, positions 0..N already carry committed rows
from earlier turns. A row-derived prefix computed on the first wake would find them all committed and
release every one — **with its OLD html.** Only the turn-scoped state knows what *this* turn produced.

**Why the polling path cannot use state:** `poll_chat` may be served by a different uvicorn worker from
the one running the graph, so there is no state to read.

The two must nonetheless agree on the **rule**. Keep the agreement test, and note it must sweep
**every** cursor: driven at cursor 0 alone it passes even with a filter-before-scan defect present,
because 0 is the one cursor at which both rules agree regardless. `slides_since_cursor`'s prefix scan
therefore **always starts at position 0, never at the cursor.**
