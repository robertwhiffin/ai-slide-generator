## 2. BLOCKING — a conditional-edge router SEES the writes of the node it hangs off. C4 as written builds nothing.

**[measured]** Probe, on the installed langgraph:

```python
def writer(state):
    print("NODE sees marks =", state.get("marks"))
    return {"marks": {"a": 1}, "log": ["node ran"]}

def router(state):
    print("ROUTER sees marks =", state.get("marks"))
    return "end"

g.add_conditional_edges("writer", router, {"end": END})
```

Output:

    NODE sees marks = {}
    ROUTER sees marks = {'a': 1}
    ROUTER sees log   = ['node ran']

**Why this breaks C4 exactly as drawn.** C4 has `foreman_node` write
`dispatched_at = scoped(turn_id, {p: now})` for "the positions it actually dispatches", and then
`foreman_router` decide the batch. But `next_dispatch_batch` excludes in-flight positions
(C2 rule 2), and by the time the router runs, the node's stamps have landed — so every position
the node just stamped now reads as in-flight, the router's `next_dispatch_batch` returns `[]`,
the turn falls through to `END`, and **the graph builds nothing while every C2 unit test stays
green.** That is precisely the "scheduler test passes while the shipped topology degrades" failure
spec §8 warns about, arriving through a channel neither C2 nor C5 names.

**Ruling C-1: `foreman_node` decides the batch, and `foreman_router` reads the decision out of
`foreman_wakes` — it MUST NOT call `next_dispatch_batch`.**

`foreman_wakes` is already the declared channel for exactly this: C4 requires a wake recorded on
**every** foreman entry, including one that dispatches nothing (`[]`), and says the reconciliation
rule "reads the most recent entry". So:

- `foreman_node` computes the batch **once**, stamps `dispatched_at` for it, and appends it to
  `foreman_wakes` as `scoped(turn_id, [batch])`.
- `foreman_router` reads the **last** entry of `scoped_vals(state, "foreman_wakes")`. Non-empty →
  `[Send("builder", build_branch_payload(state, p)) for p in that batch]`. Empty → fall through to
  the fixer / placeholder / deck-reviewer / END ladder.
- The router calls `next_dispatch_batch` **nowhere**. A reviewer seeing it there should treat it as
  a defect.

Cost if wrong: the router and node could disagree about the batch. They cannot, because there is
exactly one producer of the decision and the router only reads it.

## 3. BLOCKING — `stalled_positions` limb 1 and C4's decision ORDER are mutually unsatisfiable. Reorder the node.

C4 states the foreman's precedence as `fix → stall → dispatch → all-committed → END`, and
`stalled_positions` limb 1 as *"has a `dispatched_at` entry, **is NOT in the most recent
`foreman_wakes` batch**, and is neither landed nor placeheld"*.

**Traced against the barrier, those two cannot both hold** [measured reasoning over the plan's own
runtime facts; no code exists yet to run]. Three-slide deck, position 1's builder dies without
placeholding:

- wake 1: `dispatched_at` empty → batch `[0,1,2]`, wake `[0,1,2]`, stamps `{0,1,2}`.
- barrier: the batch completes; 0 and 2 land, 1 does not.
- wake 2: position 1 has a `dispatched_at` entry, is not landed, is not placeheld — **but it IS in
  the most recent wake `[0,1,2]`, so limb 1 excludes it.** Limb 2 does not apply either (limb 2 is
  *"a `dispatched_at` entry with NO wake record in this turn"*). `next_dispatch_batch` returns `[]`
  because position 1 is outstanding-but-in-flight. Not all committed → **`END`, with a slide
  missing, no placeholder, no `error_state` and nothing in chat** — the exact outcome C4 forbids
  two paragraphs later.

The plan's own C2 test intent pins limb 1's wording (*"a dispatched, uncommitted position outside
the most recent wake's batch is stalled at zero elapsed time … while one inside that batch is
not"*), and C4 defends the exclusion at length as the guard that keeps the limb safe "if the
runtime ever does wake the foreman mid-batch". The terse precedence pseudocode is the weaker of
the two statements.

**Ruling C-2: keep `stalled_positions`' predicate verbatim and reorder `foreman_node`'s decision
so the stall check runs AFTER the batch is computed, found empty, and the empty wake recorded.**
The node's order becomes:

    1. has_pending_fix(state)                     -> "fixer",  wake [], stamp nothing
    2. batch = next_dispatch_batch(state)
    3. batch non-empty                            -> Sends,    wake [batch], stamp dispatched_at
    4. batch empty, stalled_positions(state')     -> "placeholder", wake [], stamp nothing
    5. all_positions_committed(state)             -> "deck_reviewer", wake []
    6. otherwise                                  -> END + error_state (see C4's own rule)

where `state'` is the state the router will see — i.e. with this entry's **empty** wake already
appended, which is what makes limb 1 fire on positions left over from the completed batch.
`foreman_router` mirrors this ladder, taking the batch from the last wake per Ruling C-1 and
never recomputing it.

Consequence, and it is a behaviour choice worth stating: **a stalled position is placeheld one
wake later than the plan implies** when there is still unstarted work — the foreman dispatches the
real work first and reconciles when the queue drains. That is strictly better than placeholding
while builders are available, and it costs one extra superstep.

Cost if wrong: on a runtime that woke the foreman mid-batch, a still-running position would be
excluded from limb 1 (safe) rather than placeheld (unsafe) — the exclusion is preserved, so this
ruling makes the limb strictly safer than dropping it, and reachable, which it was not.
