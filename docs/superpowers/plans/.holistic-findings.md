# Holistic cross-plan handoff review — findings (working file)

15 findings. ✅ = I verified against the code/plans myself.

## Severe — silent data loss or execution-blocking

**F10 ✅ EXPORT LOSES ALL DECK CSS + Chart.js CDN, and the test reports green.**
`export.py:52-53` reads `slide_deck.get("external_scripts", [])` and
`.get("css", "")`. PR1's row-branch returns `"css": deck.css or ""` and
`"external_scripts": []  # TODO` (pr1:1111-1112), and **neither dual-write
(Task 4) nor backfill (Task 3) populates `deck.css` or any external-scripts
store**. So the moment rows exist, every PPTX/Google-Slides export loses deck
CSS and the Chart.js tag — the PRD §3 no-regression gate — and PR1's Task 8
export-parity test is written as `pass` stubs (2 of them), so CI stays green.
→ PR1 must populate css/external_scripts on dual-write AND backfill, and the
parity test must actually assert.

**F2 ✅ `SlideWriter()` cannot be instantiated as PR3 calls it.**
PR1: `def __init__(self, session_manager: SessionManager)` (pr1:1268). PR3
calls bare `SlideWriter()` at **10 sites**. TypeError at every one. PR1's
Handoff block publishes method signatures but no constructor — that is how it
got through. Graph nodes are pure functions of GraphState (no session_manager),
so **PR1 should default it** (`session_manager=None` → `get_session_manager()`).

**F12 ✅ `write_slide_verification` destroys content-hash keying.**
Spec §3.2/§5.2.4 keep hash keying so findings survive regeneration. PR1
(1540-1567) does `row.verification_record = json.dumps(record)` — a whole-field
overwrite, so writing a new hash discards the previous one's findings. Current
code merges first (`session_manager.py:1136-1147`). → merge within the row
(safe now: one row per reviewer).
Same contract: PR1's docstring promises `VersionConflictError` (pr1:60-61) but
the implementation never raises it and PR3 assumes "no optimistic lock on the
slide row" (pr3:44). Delete the raise clause.

**F15 ✅ Dual-write leaves orphan rows when a deck shrinks.**
PR1 iterates `enumerate(slides)` update-or-insert (973-1006), never deleting
rows above the new count. Delete-slide and restore-to-shorter both leave stale
higher positions; the read path prefers rows whenever any exist (1101-1105), so
`get_slide_deck()` returns MORE slides than the deck has — and PR3's
`releasable_positions` / all-landed trigger inherit phantom positions.
→ `DELETE WHERE position >= len(slides)` in the same transaction.

**F6 ✅ Nothing writes `SlideDeckVersion.deck_spec_json`.**
Spec §4.4 requires save points snapshot the spec. PR1 adds the column and a
test asserting restore preserves it (pr1:1671) but never touches the writer at
`session_manager.py:1258-1264` (constructs SlideDeckVersion with no spec arg)
nor the restore reader (:1408-1430). PR1's Task 9 test cannot pass.
→ PR1 owns the write (it owns the column and the save-point code).
